# SGF parser experiment

This directory evaluates the independent `crates/sgf` library from
[lizzieyzy-next-v2 at c1718bb](https://github.com/wimi321/lizzieyzy-next-v2/tree/c1718bbefe4c2149f545db5b7bb191c7b37b7b27/crates/sgf).
It does not replace KG's parser or serializer, add a native library to the application,
or participate in the normal Maven build. The upstream crate and this wrapper are
GPL-3.0-only. Cargo pins the upstream revision; the committed lockfile pins its dependency graph.

See the [2026-11-12 findings](RESULTS.md) and [raw evidence](results/2026-11-12.json).

## Run

Use JDK 21 (the Java probe targets Java 17), Maven, Python 3.10+, and Rust 1.96+.
The first build needs access to Maven Central, GitHub and crates.io. Use a disposable
development checkout, with no other Maven process writing to its `target` directory.

```bash
python3 scripts/run_sgf_rust_probe.py --samples 5 --warmups 2
```

`--maven /path/to/mvn` or `LIZZIE_MAVEN` selects a Maven wrapper. `JAVA_HOME` selects
the JDK; Cargo/rustc are taken from `PATH`. `--output` must name a new directory.
The default output is a unique directory under `target/sgf-rust/`.
No application, engine, display server, or GPU is required.

The runner compiles the existing Java tests for their fixture generator, builds the Rust
wrapper with `--release --locked`, and compiles the Java bridge separately. It records
source/fixture/binary hashes, the KG revision and dirty state, crate revision, tool versions,
warnings, errors, all timing samples, and summary tables. Rust children use bounded requests
and are terminated when the probe closes. Build and overall probe timeouts are also bounded.

## Comparison boundary

The corpus combines four checked-in SGFs, the four large fixtures generated by
`SgfPerformanceProbe.writeFixtures`, and diagnostic inputs for extensions, property order,
escaping, compressed setup ranges, malformed input, deep branches, collections, and legacy
encodings. Valid primary/secondary `KGP` provenance and stale-digest controls also exercise
analysis source retention and invalidation. Original file bytes go to Rust; KG uses its existing `SgfFileReader` decoder.

The Rust process returns **every node, branch, property identifier and value**, not a digest
or a move count. The Java bridge materializes an immutable `SgfDocument`. Rust has already
unescaped the values, so the bridge re-escapes them once before KG's existing per-property
decoding policy. Ordered events and values are compared, then both documents are built by
the same KG history builder. A history digest covers stones, turns, node kinds, move numbers,
game information, comments, stored properties, both analysis slots, candidates/PVs,
ownership, and provenance. Zobrist random values are deliberately excluded.

The harness checks matching syntax and history controls, an altered property, and a removed branch before
running the corpus. Compatibility differences are evidence, not a failing benchmark process:
transport failures, broken controls, and Java baseline failures do fail the run. Read `summary.json`, including
`compatible`, warnings and errors; a successful process alone does not mean compatibility.

This is an intentionally minimal bridge, not a new production adapter. In particular,
Rust retains compressed setup ranges while KG's syntax stage expands them. That diagnostic
therefore identifies missing adapter work, not loss in Rust's syntax tree. A collection is
compared as syntax, but is never silently merged into one KG history. Game selection remains
an explicit future integration decision. Tolerant malformed-input handling and legacy
decoding differences are reported without declaring either parser universally correct.

## Measurements

Only fixtures with matching documents and history digests receive performance measurements.
All input is already in memory and filesystem/JVM state is warm; warmups are excluded.
Java and Rust order alternates, and every recorded sample is retained. There are no timing
assertions or inferred UI responsiveness claims.

| Measurement | Included work |
| --- | --- |
| Java syntax | Decoded `String` to complete `SgfDocument`, including KG input normalization |
| Rust parse | Raw UTF-8 bytes decoded and parsed inside the Rust library; excludes response construction |
| Rust transport + document | Java UTF-8 encoding, request/response pipes, complete Rust response construction, Java response decoding, value adaptation and `SgfDocument` allocation |
| Java history | A prepared document to a detached KG board history, including analysis payloads |
| Java total | Java syntax plus KG history construction |
| Rust total | Full warm Rust transport/document path plus the same KG history construction |
| Rust cold transport + document | Child process startup plus full transport/document path; excludes child shutdown and history construction |

Rust's internal parse time is **not** an application speedup measurement. The full transport
path includes copies that a future JNI/FFM binding might avoid, but no such binding is measured
or implied here. These results do not cover allocations/peak RSS, native packaging/signing,
cross-platform distribution, cancellation during UI loading, or GPU/engine work.

## Java integration boundary

`SgfDocument.parse(String)` has no board, engine, configuration or UI owner. It retains ordered
syntax and raw value escapes. `SGFParser.buildHistory(document, first, options)` applies an
explicit immutable `ParseOptions` snapshot and builds a private history. Each position's
Zobrist table owns its dimensions, so concurrent detached imports never resize the live
board or replace its hash tables. Parsing a different board size no longer uses reflection.
Tables of the same size reproduce the same values from a process-local random seed. This
keeps ko comparisons valid when online synchronization combines independently parsed histories,
without a global cache retaining arbitrary board sizes. Hashes are not persisted in SGF.

Legacy `parseSgf` callers keep their entry point. Callers moving work to a worker should
capture `ParseOptions` on the requesting owner first and publish the completed history through
their existing UI/engine owner. Interactive loading uses the shared syntax parser but retains
its existing installation/synchronization transaction. This change does not claim that the
entire interactive load has moved off the EDT.

Adopting Rust requires demonstrated compatibility for KG extension properties and retained
analysis, a complete adapter, and an end-to-end benefit that justifies native lifecycle and
packaging costs. Keep production Java until those criteria are met.
